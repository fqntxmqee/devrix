## 1. 问题陈述

devrix 当前配置系统在启动时加载配置后，无法动态感知配置文件（devrix.yaml）的变更。这导致：

1. **生产环境灵活性低** - 修改日志级别、LLM 参数等需要重启服务
2. **故障恢复时间长** - 配置错误修复后需重新部署
3. **调试效率低** - 无法在不中断服务的情况下测试不同配置

---

## 2. 解决方案

### 2.1 方案 A：文件系统监控 + 回调机制（推荐）

```
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│   devrix.yaml   │────▶│   FileWatcher    │────▶│ ChangeNotifier  │
│  (config file)  │     │  (fsnotify)       │     │  (pub/sub)      │
└─────────────────┘     └──────────────────┘     └────────┬────────┘
                                                          │
                        ┌─────────────────────────────────┼─────────────┐
                        │              Subscribers         │             │
                        ▼              ▼                   ▼             ▼
                  ┌──────────┐  ┌──────────┐  ┌──────────────┐  ┌──────────┐
                  │  LLM     │  │  Logger  │  │  Permission   │  │  ...     │
                  │  Gateway │  │  Service │  │  Service      │  │          │
                  └──────────┘  └──────────┘  └──────────────┘  └──────────┘
```

**优点：**
- 实时感知变更
- 声明式订阅，灵活扩展
- 解耦配置源与消费者

**缺点：**
- 依赖文件系统事件
- 需要处理并发更新

### 2.2 方案 B：定期轮询

定时检查文件 mtime，时间间隔 30 秒。

**缺点：** 延迟高、资源消耗大，**不推荐**

## 3. 实现方案 A 的详细设计

### 3.1 组件结构

```
internal/
├── evolution/
│   └── config/
│       ├── watcher.go          # 文件监控
│       ├── watcher_test.go
│       ├── notifier.go         # 变更通知
│       ├── notifier_test.go
│       └── hotreload/
│           ├── service.go      # 热重载服务
│           ├── service_test.go
│           └── options.go      # 配置选项
```

### 3.2 核心接口

```go
// Watcher 监控配置文件变更
type Watcher interface {
    Start(ctx context.Context) error
    Stop() error
}

// Subscriber 变更订阅者
type Subscriber interface {
    OnConfigChange(old, new *Config) error
}

// ConfigManager 配置管理器
type ConfigManager interface {
    Get() *Config
    Reload(path string) error
}
```

### 3.3 工作流程

1. **启动阶段**：`ConfigManager` 初始化 `Watcher`，注册自身为订阅者
2. **监控阶段**：`Watcher` 使用 `fsnotify` 监听文件变更事件
3. **变更检测**：收到 `WRITE`/`CREATE` 事件后，延迟 500ms 防抖
4. **重载执行**：
   - 解析新配置文件
   - 验证格式正确性
   - 合并变更配置项
   - 通知所有订阅者
5. **错误处理**：解析失败时，回滚到旧配置，记录错误日志

### 3.4 防抖机制

```
[Event] → [500ms Debounce] → [Check Again] → [Reload]
                │
                └── 忽略期间的重复事件
```

## 4. 风险与缓解

| 风险 | 影响 | 缓解措施 | 验证方式 |
|------|------|----------|----------|
| 文件事件丢失 | 中 | 启动时记录文件 mtime，定期校验 | TDD 模拟 |
| 配置格式错误 | 高 | defer recover + 保持旧配置 | 异常测试 |
| 回调执行失败 | 中 | 记录失败，继续通知其他订阅者 | 隔离测试 |
| 并发竞争 | 中 | 使用 Mutex 保护配置读写 | 并发测试 |

## 7. 决策

**推荐方案 A：文件系统监控 + 回调机制**

理由：
1. 实时性满足业务需求（< 5 秒）
2. 架构清晰，易于测试
3. 与现有配置体系兼容
4. 社区成熟方案，无重大风险
