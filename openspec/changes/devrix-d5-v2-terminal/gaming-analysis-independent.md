## 1. 多重均衡与均衡选择 — 为何 v2.1 不是"又一次重构"

### 1.1 诊断

D5 的演进历史可以建模为一个**多重均衡选择问题**：

```
均衡 A（Legacy S1-S9）：
  - 每个 Go 包 = 一个 S 场景号
  - 消费者按模块思维组织遥测代码
  - Tracer / Metrics / Logger 是"三个独立的东西"
  - Bridge 是访问入口

均衡 B（Canonical S21-S24）：
  - 每个价值流 = 一个 S 场景号
  - 消费者按用户目标组织遥测代码
  - Instrument 是"产生遥测的一个东西"
  - 直连 instrument/* 是访问入口
```

两个均衡在功能上**都可以工作**。v1.0 Registry 试图从 A 切换到 B，但 Bridge 的存在使 A 仍然可达，导致双轨并行的混合均衡。

### 1.2 均衡选择的核心困难

这不是"坏均衡 → 好均衡"的简单切换，而是**两个均可行的均衡之间的选择**：

| 维度 | 均衡 A (Legacy) | 均衡 B (Canonical) |
|------|----------------|---------------------|
| 学习成本 | 低（1:1 映射包→场景） | 中（需理解价值流） |
| 消费者便利 | 高（熟悉的包名） | 中（需查 registry） |
| 架构一致性 | 低（S 被 Go 绑架） | 高（S 表达 North Star） |
| 新人理解 | 低（"为什么有 9 个 S？"） | 高（"4+1 个价值流"） |
| 演化成本 | 高（每加能力需新 S） | 低（A 层扩展不增 S） |

**关键洞察：均衡 A 对当前开发者局部更优，均衡 B 对系统长期全局更优。** 这是典型的局部最优 ≠ 全局最优困境。

### 1.3 v2.1 的均衡选择策略

v2.1 采用的策略不是 "说服" 而是 "烧船"（§11.3.1）：

```
Phase A: 把文档锚点从 A 移到 B → 降低 B 的信息成本
Phase B: 删除 Bridge → 提高 A 的执行成本
```

这是**双管齐下的均衡迁移**：降低目标均衡的成本 + 提高源均衡的成本。

但在博弈论上，还有一个关键因素被忽略了：**临界质量（Critical Mass）**。

### 1.4 临界质量与网络效应

Bridge 的博弈价值不仅是 "访问路径"，还是一个**协调装置**：

```
当所有域都用 Bridge → Bridge 是谢林点 → 新域也跟从
当 D6 先删 Bridge → 临界质量开始瓦解 → D5 跟进加速
当 D5 也删 Bridge → 遗留使用者 (if any) 被孤立
```

D6 先删 Bridge（v2.0.1）不仅是一个技术先例，更是一个**博弈信号**：宣告 Legacy 均衡不再是被默认选择的谢林点。

**建议：** 在 `d5-domain.md` 的迁移记录中显式记录各域的 Bridge 删除时间线，形成一个**公共知识（Common Knowledge）**——"每个人都知道每个人都知道 Legacy 路径已死"。

## 2. 信号博弈与域名誉 — 埋点质量作为分离均衡

### 2.1 诊断

现有分析把 "业务域开发者" 建模为同质玩家（§2 玩家表）。但实际上，各业务域在**观测质量上的异质性**是一个未被利用的信息结构。

将 D5 与业务域的关系建模为**信号博弈（Signaling Game）**：

```
Sender（业务域）: 知道自己的埋点质量 θ ∈ {高, 低}（私有信息）
Receiver（D5/SRE）: 只能观察信号 s ∈ {Coverage > 80%, Coverage 不明, unknown op 频繁}
Payoff: Sender 想被 Receiver 认为 θ=高（获得信任/自治权）
```

### 2.2 分离均衡的条件

要让 "高埋点质量的域" 和 "低埋点质量的域" 发出不同信号（分离均衡），需要：

```
模仿成本（低质量域假装高质量）> 模仿收益（被当作高质量域的收益）
```

当前机制的模仿成本分析：

| 信号 | 模仿成本 | 评价 |
|------|---------|------|
| Coverage 高 | 中（需真的埋点） | 有一定的分离能力 |
| unknown op = 0 | 中高（需用 canonical op） | 较好的分离能力 |
| Span 属性完整（layer/component） | 低（Bridge 自动注入） | 无分离能力 |
| Trace 树可交叉引用 | 高（需配合 D7 的 Turn span 设计） | 强分离能力 |

**当前状态：信号空间不够丰富，难以形成稳定的分离均衡。** 高质量的域和低质量的域可能发出相似的信号。

### 2.3 增强分离均衡的建议

1. **按域分组的 Coverage dashboard（§14.5 透明度机制）**：让每个域的埋点质量**公开可见**。这不仅是透明度的技术手段，更是一个**声誉机制**——域 owner 的埋点质量成为跨域公共知识。

2. **引入 "观测债务" 概念**：类似技术债务，但专门针对可观测性。Domain owner 在 PR 中声明 "本 PR 引入 X 个新 span，均已注册"。未注册的 span 被公开追踪为 "观测债务"。

3. **利用 D6 的跨域可见性**：D6 是 Judge，评测所有域的行为质量。如果 D6 的评测报告中包含 "该域的观测完整度评分"，则 D5 的信号通过 D6 获得了**二次放大**。

**这比 "硬拒绝未注册 op"（Grill-4）更优雅：不强制，但让低质量成为公共信息。**

## 3. 重复博弈与未来的影子 — 重构周期对合作的侵蚀

### 3.1 诊断

D5 与业务域的关系不是一次性博弈，而是**无限次重复博弈**（或至少是不确定终点的有限次博弈）。

根据 Folk Theorem，在无限次重复博弈中，如果贴现因子 δ 足够高（玩家足够在乎未来），合作均衡（双方都遵守可观测性契约）是可以维持的。

但 D5 的频繁重构（v1.0 → v2.0 → v2.1）引入了一个反直觉的风险：

### 3.2 重构作为 "博弈重启"

```
每次重构 = 游戏规则改变 = 过去的合作声誉被折扣
```

| 重构 | 对业务域的信号 | 博弈后果 |
|------|---------------|----------|
| v1.0 Registry | "S 编号全换了" | 域 owner 质疑：下次还会换吗？ |
| v2.0 物理迁移 | "import 路径全换了" | 域 owner 成本：改所有 import |
| v2.1 Terminal | "bridge 删了，再换一次" | 域 owner 预期：这真的是最后一次吗？ |

**关键风险：如果业务域预期 D5 未来还会重构，δ 下降，合作激励减弱。**

### 3.3 "终态"声明作为博弈承诺

v2.1 的命名 "Terminal" 本身就蕴含了一个博弈承诺："这是最后一次大规模重构"。

但这个承诺的**可信度**取决于：
1. 是否在公共文档中显式声明（而不仅是 change 名称）
2. 是否有制度约束防止未来的随意重构
3. 过去的承诺是否被遵守（D6 bridge 删了之后没有再恢复——正面先例）

**建议：**
- 在 `d5-domain.md` 中写入 **"冻结声明"**：S21–S24 号段、物理路径、Operation Registry 56 条均声明为长期冻结
- 声明任何未来的 S 层变更需要 **D5 Owner + 2 个业务域 Owner 的 NACK 权**——提高制度性变更成本
- 将 T ID 不变策略推广为 **"T 层宪法"**——任何改动 T ID 的提案需要跨域 Review

### 3.4 修复信任的时间窗口

```
δ = 1 / (1 + r)，其中 r = 贴现率
```

业务域的 "贴现率 r" 与 "D5 的重构频率" 正相关。v2.1 Terminal 之后，D5 需要一个**足够长的稳定期**来证明 "Terminal" 是真的 Terminal，从而降低 r，提高 δ，恢复合作激励。

**量化的经验法则：至少 2 个 release cycle（~2 个月）不进行 S 层或物理路径变更。**

## 4. 公共池资源治理 — Operation Registry 作为 CPR

### 4.1 诊断

`gaming-analysis.md` §13.5 将 Coverage 报告建模为公共物品。但**Operation Registry 本身更准确地应建模为公共池资源（Common Pool Resource, CPR）**：

| 属性 | Coverage 报告 | Operation Registry |
|------|--------------|-------------------|
| 竞争性 | 非竞争性（公共物品） | **竞争性** — 增加 op 增加维护成本 |
| 排他性 | 非排他性 | 非排他性 — 任何域都能注册 op |
| 资源类型 | Pure Public Good | **Common Pool Resource** |

CPR 的经典悲剧（Hardin, Ostrom）：

```
每个域局部最优：多注册 op → 更细粒度的追踪
全局后果：Registry 膨胀 → 维护成本上升 → on-call 难以理解 Trace 树
```

当前 56 ops 规模尚可控，但没有**治理机制**防止未来膨胀到 200+ ops。

### 4.2 Ostrom 八项设计原则的应用

Elinor Ostrom 的 CPR 治理八原则可以用于设计 Registry 的长期治理：

| Ostrom 原则 | D5 Registry 对应 | 当前状态 |
|-------------|-----------------|----------|
| 1. 明确边界 | 哪些域可以注册 op？ | ✅ 明确（D1–D7） |
| 2. 规则与本地条件匹配 | Op 命名规范（`D{N}_{场景}_{动作}_{细节}`） | ✅ v2.1 建立 |
| 3. 集体决策 | 谁决定新增/删除 op？ | ⚠️ **不明确** — 目前 D5 单方面管理 |
| 4. 监督 | 谁审计 Registry 的完整性？ | ✅ Coverage + span-registry |
| 5. 分级制裁 | 违规注册 ad-hoc string 的后果？ | ⚠️ **仅 WARN** — 可能有制裁阶梯 |
| 6. 冲突解决 | 两个域对同一 op 语义有争议？ | ❌ 无机制 |
| 7. 最低限度的外部承认 | D5 的 Registry 管理权被其他域承认？ | ✅ 通过 CLAUDE.md 约定 |
| 8. 嵌套式治理 | 大型 CPR 需要多层治理 | ⚠️ Operation Registry 56 条尚小，暂不需要 |

### 4.3 具体建议

1. **建立 Op 新增/删除的决策流程**（Ostrom 原则 3）：PR 新增 op 时需在 `span-registry.md` 中说明 "新增理由 + 归属域 + 消费者"，D5 Owner Review。

2. **建立分级制裁阶梯**（Ostrom 原则 5）：

```
第 1 次 unknown op: WARN 日志 + metric
第 2 次同域 unknown op: Coverage 报告标记 "可疑"
第 N 次同域 unknown op: D6 advisory 降级该域的行为可信度
```

3. **设置 Registry 容量上限**（预防性规则）：Ops 总数 ≤ 100。超过 100 时触发 Registry 审计（删除 RETIRED、合并冗余）。

## 5. 无强制力的机制设计 — D5 的根本约束

### 5.1 诊断

D5 的核心博弈困境可以总结为：

> **如何在不拥有强制力（enforcement power）的前提下，诱导业务域诚实地产生可观测性数据？**

这是**机制设计（Mechanism Design）**的经典问题——设计者（D5）想要实现某个社会选择函数（全局可观测），但参与者（业务域）拥有私有信息和私有行动空间。

### 5.2 现有装置的机制设计分类

| 装置 | 机制类型 | 激励相容？ | 局限 |
|------|---------|-----------|------|
| Bridge 注入 | 降低合规成本（nudge） | 部分相容 | 不强制使用 |
| Op 常量 | 命名收敛（focal point） | 相容 | 仅限已使用的 op |
| Coverage 报告 | 信息披露（transparency） | 弱相容 | 需要被读才有激励 |
| WARN unknown op | 社会压力（social pressure） | 弱相容 | 仅在有人看日志时有效 |
| RecordHit | 不可否认性（non-repudiation） | 相容 | 已埋点的路径 |
| FaultInject | 红队测试（red team） | testbuild only | 不覆盖生产 |

**整体评估：D5 的机制工具箱偏向 "软机制"（信息披露 + 社会压力 + 降低合规成本），缺少 "硬机制"。**

但 §11（Grill-4）已经正确论证了 "硬拒绝未注册 op" 不是正确答案——硬机制会触发业务域的策略性规避（fork registry）。

### 5.3 软机制的强化路径

核心问题不是 "软 vs 硬"，而是**软机制的信号传递是否足够强**：

1. **从 "被动 WARN" 到 "主动推送"**：当前 WARN 是日志中的一行——业务域可以无视。如果 WARN 聚合为 metric → 进入 on-call dashboard → 在 PR review 中被引用，信号的**送达率**大幅提高。

2. **从 "匿名漂移" 到 "归因漂移"**：unknown op 携带 `devrix.layer` 属性 → 追溯到域 → 域 owner 无法推卸。这是将**外部性内部化**：让产生 unknown op 的域承担声誉成本。

3. **从 "D5 独自审计" 到 "D6 联合审计"**：D6 的评测报告中引用 D5 的观测完整度——D5 的信号通过 D6 获得制度性权重。

4. **从 "事后发现" 到 "事前承诺"**：PR 模板勾选 "新增 Span 是否在 Registry 注册"——让开发者在代码合入前做出可验证的承诺。

### 5.4 一个被忽视的机制：基准测试（Benchmarking）

未被利用的激励装置：**按域分组的观测质量排行榜**。

```
D1 Coverage: 92% | unknown op: 0 | span 属性完整度: 100%
D2 Coverage: 88% | unknown op: 2 | span 属性完整度: 95%
D4 Coverage: 45% | unknown op: 7 | span 属性完整度: 60%
```

排行榜不强制任何行为，但创造了**横向比较的压力**。域 owner 看到自己在榜单底部，自发动机改进。这比 "硬拒绝" 或 "强制消费义务"（§14.5 已正确拒绝）更符合 D5 的 Referee 定位。

## 6. 信息级联与迁移次序 — 为何 D6 先、D5 现在是正确的

### 6.1 诊断

现有分析未讨论各域迁移的**次序（ordering）**对博弈结果的影响。

Devrix 的迁移次序：

```
D6 v2.0.1（删 bridge，建 d6-domain）→ 2026-06-15
D7 v2 Structure（终态闭合）→ 2026-06-19
D5 v2.1 Terminal（本 change）→ 2026-06-19
D2 / D1 / D4 尚未进入 terminal 阶段
```

### 6.2 信息级联模型

```
D6 删 bridge（先例）→ D7 参考 D6 模式 → D5 参考 D6+D7 模式
```

这是一个**信息级联（Information Cascade）**：每个后续迁移者观察到先行者的结果，更新自己的信念，然后跟随。

但信息级联有两个风险：
1. **级联脆弱性**：如果先行者（D6）的选择被发现有问题，整个级联崩溃
2. **次序锁定**：后行者可能盲目模仿先行者的模式，而不考虑自身特点

### 6.3 D6 作为先行者的博弈含义

D6（演化层）作为 bridge 删除先行者是正确的次序选择：

| D6 先行 | D7 或 D5 先行 |
|---------|--------------|
| D6 是支撑域，bridge 使用量最低 | D7 是核心域，bridge 使用量最高 |
| 删除风险最低 → 低成本验证 | 删除风险最高 → 高成本试错 |
| 低风险先行的信息最有价值 | 高风险先行失败会阻止后续迁移 |

**D6 先行的博弈智慧：用最低赌注验证 "bridge 可安全删除" 的假说，成功后将这一信息作为公共知识传递给后行者。**

### 6.4 D5 现在迁移 vs 等待

D5 选择此刻进入 v2.1 Terminal 的时机判断：

| 因素 | 评价 |
|------|------|
| D6 已验证 bridge 可删 | ✅ 有可信先例 |
| D7 已验证终态闭合模式 | ✅ 有参考模板 |
| D2/D1/D4 尚未 Terminal | ⚠️ D5 先于其他核心域进入 Terminal |
| D5 自身 41 T 高完成度 | ✅ 迁移基础扎实 |

**建议：D5 v2.1 Terminal 将成为 D2/D1/D4 的 "第三个先例"。三个先例（D6 + D7 + D5）构成足够强的信息级联，使后续域的 Terminal 迁移几乎没有决策阻力。**

## 7. Bridge 作为关联均衡装置 — 删除的深层博弈含义

### 7.1 诊断

`gaming-analysis.md` §11.3.1 将 Bridge 删除建模为 "烧船承诺"。这是一个正确的但不够完整的视角。

更精确的建模：**Bridge 是一个关联均衡装置（Correlated Equilibrium Device）。**

### 7.2 Bridge 的协调功能

```
在 Legacyd 均衡中：

D2 开发者写: import "observability/tracer" → 创建 span
D7 开发者写: import "observability/tracer" → 创建 span
D4 开发者写: import "observability/tracer" → 创建 span

不需要互相知道对方的选择；Bridge 作为公共信号协调所有人的行为。
```

**Bridge 的本质：降低跨域协调成本的中间层。** 没有 Bridge 时，每个域需要：
- 知道 `instrument/tracer` 的正确路径
- 知道 `Op*` 常量的位置
- 知道 `RecordHit` 的语义

Bridge 将这些决策打包成一个 "默认选项"，使开发者不需要全局知识就能做出局部正确的选择。

### 7.3 删除 Bridge 的代价

删除 Bridge 不仅删除了 "撤退选项"（烧船），还**提高了新开发者的学习成本**：

```
有 Bridge: import "observability/tracer" → 用 tracer.Start() → 一个 import 搞定
无 Bridge: import "observability/instrument/tracer" → 用 tracer.Start()
           import "observability/instrument/telemetry" → 用 Op* 常量
           需要理解 Bridge 的注入模式 → 更高认知负荷
```

但**这个代价是值得的**，因为：
1. 学习成本的 "一次性增加" 换取 "永久的架构清晰"
2. `instrument/` 前缀本身就是文档——"这是 Instrument 场景（S21）的产出"
3. 开发者被迫理解 DSAFT 分层，而非依赖 Bridge 的隐含映射

### 7.4 从关联均衡到纳什均衡

```
Legacy:    Bridge = 关联均衡装置 → 低成本协调
Canonical: 直连 = 纳什均衡        → 每个域独立选择 canonical 路径
```

在 canonical 均衡中，每个域**不需要外部协调装置**就能做出正确选择——因为 `instrument/tracer` 路径本身就是谢林点（唯一合理的选择）。

**这是比 "烧船" 更深的博弈含义：不是强制新均衡，而是让新均衡成为唯一的谢林点，从而使关联均衡装置（Bridge）变得多余。**

---

## 8. S23 子承诺的博弈边界 — 一个被忽略的逆向风险

### 8.1 诊断

现有分析聚焦在 S23 是否膨胀（OQ-1, Grill-3），但忽略了一个逆向风险：

> **子承诺（C3a–C3e）的显式登记，可能反而激励 "能力蔓延"。**

### 8.2 子承诺作为 "菜单"

```
当 C3a Coverage → C3b Incident → C3c Doctor → C3d Tracker → C3e FaultInject
以子承诺形式列出后，D5 开发者看到的不是 "5 个已有能力"，而是 "5 个槽位，可以再加第 6 个"。
```

这是**菜单效应（Menu Effect）**——显式列出的子承诺结构鼓励填充新的子承诺，就像空白表格鼓励填写。

### 8.3 预防机制

现有分析已经提出了硬边界（语义/数量/依赖，Grill-3），但缺一个：

**子承诺新增的 "举证责任"：** 任何提议新增 C3f 的提案，必须证明：
1. 该能力无法归入现有 C3a–C3e
2. 该能力的消费者与现有子承诺的消费者不同
3. 新增不导致 S23 超过 7 个子承诺上限

这实际上是**提高 "供给方" 的决策成本**——不是禁止新增，而是让新增需要更有力的论证。
