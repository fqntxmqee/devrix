# DSAFT 架构方法论

**版本:** 1.1.0
**状态:** Active
**所属阶段:** S2、S3
**来源:** 项目级架构方法论，从 workspace 根 `specs/dsaft-architecture-methodology.md` 同步并适配 devrix
**关联规范:** `architecture-design.md`、`testing.md`、`requirements.md`

---

> 定义软件的五层架构体系：**D 领域 → S 场景 → A 活动 → F 功能点 → T 测试点**。
> 核心思想：从抽象全貌到具体实现，每层有明确定义和归属关系。

---

## 一、精确定义

| 层级 | 定义 | 核心问题 |
|------|------|----------|
| **D 领域** | 业务能力边界，划分业务内聚区 | 系统由哪些业务领域组成 |
| **S 场景** | 用户达成完整目标的业务价值流 | 谁、为了什么、走哪条路径 |
| **A 活动** | 用户/调用方发起的具体业务动作 | 对外能做什么动作 |
| **F 功能点** | 可被 A 编排的最小业务/技术逻辑单元 | 内部由哪些功能点协作 |
| **T 测试点** | 不变的验证契约（WHAT，非 HOW） | 功能是否正确工作 |

---

## 二、设计理念

### 2.1 两大分段

```
┌─────────────────────────────────────────────────────────────┐
│  DS — 抽象层（概念稳定）                                    │
│    D  业务能力边界                                          │
│    S  达成目标的路径                                        │
├─────────────────────────────────────────────────────────────┤
│  AFT — 具体层（实现易变）                                   │
│    A  对外动作（入口契约）                                  │
│    F  对内功能点（编排实现）                                │
│    T  验收锚点（不变契约）                                  │
└─────────────────────────────────────────────────────────────┘
```

**稳定性梯度**：D/S 最稳定 → A/F 易变 → T 最稳定（不变契约）

### 2.2 自上而下（分解）

```
D 领域 → S 场景 → A 活动 → F 功能点 → T 测试点
   ↓         ↓         ↓         ↓
  包含      包含     编排      验证
```

### 2.3 自下而上（追溯）

```
T → F 或 A → S → D
↑    ↑         ↑    ↑
验证 归属      归属 归属
```

---

## 三、追溯规则

| 规则 | 说明 |
|------|------|
| S → D | 每个 S 必须归属一个 D |
| A → S | 每个 A 必须归属一个 S |
| F → A | 每个 F 必须归属一个 A |
| T → F 或 A | 每个 T 必须归属一个 F 或 A |

**说明**：T 可以归属 F（验证功能点，如单元测试），也可以归属 A（验证活动，如契约测试、E2E）。

---

## 四、ID 格式规范

嵌套归属编号，格式如下：

| 层级 | 格式 | 位数 | 示例 |
|------|------|------|------|
| D | D{1-9} | 1位 | D1 |
| S | D{X}-S{X} | 1+1位 | D1-S1 |
| A | D{X}-S{X}-A{01-99} | 1+1+2位 | D1-S1-A01 |
| F | D{X}-S{X}-A{XX}-F{01-99} | 1+1+2+2位 | D1-S1-A01-F01 |
| T | D{X}-S{X}-A{XX}-T{01-99} 或 D{X}-S{X}-A{XX}-F{XX}-T{01-99} | 1+1+2+2+2位 | D1-S1-A01-T01 或 D1-S1-A01-F01-T01 |

**T 归属规则**：
- T 归属 A：D1-S1-A01-T01（验证整个活动，如契约测试、E2E）
- T 归属 F：D1-S1-A01-F01-T01（验证具体功能点，如单元测试）

链路追溯示例：
```
D1-S1-A01-F01-T01
└─ D1: 交易领域
   └─ S1: 交易下单场景
      └─ A01: 下单渲染活动
         └─ F01: 获取商品详情功能点
            └─ T01: 商品信息展示正确测试点
```

## 五、层级定义

### 5.1 D 层：领域（Domain）

**定义**：业务能力边界，划分业务内聚区。

- 有自己的业务规则和 invariants
- 有自己的数据模型（不与其他领域共享）
- 通过 A 层（活动）与其他领域交互

**D 层注册表**：

| ID | 名称 | 类型 | 领域职责 |
|----|------|------|----------|
| D1 | {领域名} | 核心/支撑/公共 | {职责描述} |

**领域类型**：
- **核心域**：核心竞争力，直接创造用户价值
- **支撑域**：支撑核心域运转，不直接面向用户
- **公共域**：横向共享能力，为其他域提供通用服务。有自己的数据模型，通过 A 层暴露，保持内部内聚

### 5.2 S 层：场景（Scenario）

**定义**：用户达成完整目标的业务价值流。

**S 层注册表**：

| ID | 名称 | 触发条件 | 用户目标 | 涉及 A |
|----|------|----------|----------|---------|

**约束**：每个 S 必须归属一个 D

### 5.3 A 层：活动（Activity）

**定义**：用户/调用方发起的具体业务动作。

分为：
- **A-BE**：后端活动，原子业务步骤，有输入/输出/状态变更
- **A-FE**：前端页面，用户可见的路由级交互单元

**A 层注册表**：

| ID | 名称 | 类型 | 输入 | 输出 | 状态变更 |
|----|------|------|------|------|----------|

**约束**：每个 A 必须归属一个 S

### 5.4 F 层：功能点（Function）

**定义**：可被 A 编排的最小业务/技术逻辑单元。

分为：
- **F-BE**：后端功能点，可复用的逻辑计算或数据操作
- **F-FE**：前端模块，可复用的 UI + 逻辑单元

**F 层注册表**：

| ID | 名称 | 类型 | 输入 | 输出 |
|----|------|------|------|------|

**约束**：每个 F 必须归属一个 A

### 5.5 T 层：测试点（Test）

**定义**：不变的验证契约，描述 WHAT should work，而非 HOW。

**T 层注册表**：

| ID | 名称 | 归属层级 | 归属 ID | 验收契约 |
|----|------|----------|---------|----------|
| D1-S1-A01-T01 | {测试点} | A | D1-S1-A01 | {契约} |
| D1-S1-A01-F01-T01 | {测试点} | F | D1-S1-A01-F01 | {契约} |

**约束**：每个 T 必须归属一个 A 或 F

## 六、测试类型与层级映射

| 测试类型 | 验证范围 | 归属层级 | 执行时机 |
|----------|----------|----------|----------|
| 单元测试 | 单个 F 内部逻辑 | F | 每次构建 |
| 集成测试 | A 编排 + 多 F | A + F | CI |
| 契约测试 | 对外接口契约 | A | CI |
| E2E | 完整 S 用户体验 | A | 发布前 |

## 八、资产登记 Checklist

| 层级 | 必填项 | 上游归属 |
|------|--------|----------|
| D | ID、名称、类型、领域职责 | - |
| S | ID、名称、触发条件、用户目标 | 归属 D |
| A | ID、名称、输入、输出、状态变更 | 归属 S |
| F | ID、名称、输入、输出 | 归属 A |
| T | ID、名称、归属层级、归属 ID、验收契约、优先级 | 归属 A 或 F |

## 九、OpenSpec 映射

| 阶段 | DSAFT 产出 | 说明 |
|------|-----------|------|
| proposal | D + S | 需求草案（领域 + 场景定位） |
| specs | A | 对外规格（活动/页面） |
| design | F + A↔F | 技术设计（功能点 + 编排） |
| tasks | F 实现任务 | 任务清单，标注归属 T |
| verify | T | 验收标准，P0 全绿方可交付 |

## 十一、历史：T 层编号体系（原 L5）

> Devrix 在引入 DSAFT 之前使用 `{T}-{D}-{S}-{NN}` 编号体系管理测试点。DSAFT 方法论中 L5 即 T 层，因此 L5 编号统一替换为 DSAFT T 层标准格式 `D{X}-S{X}-A{XX}-T{XX}`。旧 L5 条目在 `openspec/t-registry.md` 中逐步迁移。
