# 分层规范迁移指南

## 方案对比

| 维度 | 方案 A (L1-L2) | 方案 B (D-S-A-F-T) |
|------|---------------|-------------------|
| **ID 格式** | `L5-{L1}-{L2}-{NN}` | `{D}-{S}-{A}-{F}-{T}` |
| **层次数** | 2 层 | 5 层 |
| **示例** | `L5-2-1-09` | `D02-S02-A03-F03-T01` |
| **语义** | 纯技术分层 | 业务语义分层 |
| **学习成本** | 低 | 中 |
| **适用场景** | 技术架构对齐 | 需求/业务对齐 |
| **代码注释** | 可读 | 更可读 |

---

## 方案 A: L1-L2 二级分层 (技术导向)

```
L1 (顶层层) + L2 (子模块)
```

**优点**:
- 简单直接，与目录结构一一对应
- 适合纯技术团队
- ID 简短

**缺点**:
- 缺乏业务语义
- 无法区分"不同业务场景"
- 不利于需求追溯

---

## 方案 B: D-S-A-F-T 五层分层 (业务导向)

```
Domain → Scenario → Activity → Feature → Test
  │         │          │         │        │
  D01      S01        A01       F01      T01
```

**优点**:
- 完整的业务语义
- 可追溯：测试点 → 功能 → 活动 → 场景 → 领域
- 适合需求管理、PRD 追踪

**缺点**:
- ID 较长
- 需要维护更多映射表

---

## 推荐：混合方案

**最佳实践**: 结合两者优势

```
{D}-{S}-{A}-{F}     # 业务分层 (4段)
    +
L5-{T}              # 保持 L5 前缀用于测试点
```

**实际使用**:

| 场景 | 推荐方案 |
|------|----------|
| 新项目启动 | D-S-A-F-T (方案 B) |
| 快速迭代 | L1-L2 (方案 A) |
| 需求文档关联 | D-S-A-F-T |
| 测试用例编号 | L5-{T} |
| 代码注释 | 两者皆可 |

---

## 迁移路径

### Phase 1: 建立双轨制

```
openspec/specs/architecture/
├── layering.md        # 方案 A (技术参考)
├── layering-v2.md    # 方案 B (业务参考)
└── MIGRATION.md     # 本文件
```

### Phase 2: 逐步迁移

1. 新增功能使用 D-S-A-F-T 编号
2. 旧功能保持 L1-L2 编号
3. 建立映射表 (`layering-v2.md` 最后一节)

### Phase 3: 统一

- 维护映射表
- 定期审查
- 长期目标: 统一到 D-S-A-F-T

## 选择建议

| 你的团队 | 推荐方案 |
|---------|---------|
| 小团队 (< 5人) | 方案 A (简单) |
| 中型团队 (5-20人) | 方案 B (可追溯) |
| 大型团队 / 需求驱动 | 方案 B + ADRs |
| 多产品线 | 方案 B (按产品划分 Domain) |

---

## 最终推荐

对于 Devrix 这样的 **多智能体开发助手**，推荐：

### 采用方案 B (D-S-A-F-T)

理由:
1. **需求可追溯**: 从用户故事到测试用例
2. **多 Agent 场景**: 需要清晰的业务分层
3. **长期维护**: 语义清晰的 ID 更易理解
4. **文档友好**: PRD、Issue 可以直接引用 ID

### 实施步骤

1. ✅ 已创建 `layering-v2.md` (完整规范)
2. ⬜ 更新 `l5-registry.md` 使用新格式
3. ⬜ 建立旧 ID → 新 ID 映射
4. ⬜ 文档规范: 所有新文档使用 D-S-A-F-T
5. ⬜ 代码注释添加 ID 标注
6. ⬜ CI 检查: 确保测试文件与 ID 一致
