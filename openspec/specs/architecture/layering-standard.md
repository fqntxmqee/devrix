## 1. 背景与目标

### 1.1 问题陈述

Devrix 作为多智能体开发助手，需要一套统一的 ID 规范来：

- **标识**: 唯一标识所有业务能力（需求、功能、测试）
- **追溯**: 建立从领域到测试点的完整链路
- **导航**: 快速定位代码、文档和测试用例

### 1.2 设计原则

1. **业务语义优先**: ID 应反映业务含义，而非纯技术位置
2. **可扩展**: 支持未来新增领域和场景
3. **可读**: 人类可快速理解 ID 含义
4. **可追溯**: 测试点能反向追溯到需求

## 2. 推荐方案: D-S-A-F-T 五层分层

### 2.1 格式定义

```
{D}-{S}-{A}-{F}-{T}
  │   │   │   │   └── T: 测试点 (Test Point)     01-99
  │   │   │   └────── F: 功能点 (Feature Point)   01-99
  │   │   └────────── A: 业务活动 (Activity)        01-99
  │   └────────────── S: 场景 (Scenario)           01-99
  └────────────────── D: 领域 (Domain)            01-99
```

### 2.2 完整示例

```
D02-S02-A03-F03-T01
│  │   │   │   │   └── 验证超时处理测试
│  │   │   │   └────── 命令验证执行器
│  │   │   └────────── 结果验证活动
│  │   └────────────── PEV 执行场景
│  └────────────────── 上下文领域
```

## 3. 备选方案: L1-L2 二级分层

### 3.1 格式定义

```
L5-{L1}-{L2}-{NN}
     │    │    │
     │    │    └── 序号 (01-99)
     │    └─────── L2 子模块 (1-9)
     └──────────── L1 顶层层 (1-9)
```

### 3.2 完整示例

```
L5-2-1-09
   │  │  │
   │  │  └── 第 9 个功能点
   │  └───── PEV 子模块
   └──────── CTX 领域
```

### 3.3 L1 顶层层定义

| L1 | 名称 | 描述 |
|----|------|------|
| 1 | META | 元数据、系统级配置 |
| 2 | CTX | 上下文管理 |
| 3 | COMM | 通信层 |
| 4 | LLM | LLM 网关 |
| 5 | AGENT | 多智能体 |
| 6 | OBS | 可观测性 |
| 7 | EVO | 演化升级 |

### 3.4 L2 子模块示例

**L1=2 (CTX) 时 L2 定义:**

| L2 | 子模块 | 描述 |
|----|--------|------|
| 2-1 | PEV | Plan-Execute-Verify |
| 2-2 | COMPRESS | 上下文压缩 |
| 2-3 | MEMORY | 记忆管理 |

### 3.5 优缺点分析

| 维度 | L1-L2 | D-S-A-F-T |
|------|-------|-----------|
| ID 长度 | 短 (8-10 字符) | 长 (17-19 字符) |
| 语义清晰度 | 中 | 高 |
| 与目录结构对应 | 直接 | 需映射 |
| 新增场景成本 | 低 | 中 |
| 需求追溯能力 | 弱 | 强 |
| 适用团队规模 | 小 (< 10 人) | 中大 (> 10 人) |

## 4. 方案对比与选择

### 4.1 核心差异

| 维度 | L1-L2 (技术分层) | D-S-A-F-T (业务分层) |
|------|-----------------|---------------------|
| **分层依据** | 技术架构 | 业务语义 |
| **ID 语义** | `L5-{领域}-{模块}-{序号}` | `{领域}-{场景}-{活动}-{功能}-{测试}` |
| **可追溯性** | 单向追溯 | 双向追溯 |
| **适用场景** | 技术实现 | 需求管理 |

### 4.2 选择建议

| 场景 | 推荐方案 |
|------|----------|
| 小团队快速迭代 | L1-L2 |
| 中大型团队 | D-S-A-F-T |
| 需求驱动开发 | D-S-A-F-T |
| 多产品线 | D-S-A-F-T (按产品划分 Domain) |
| 技术债清理 | L1-L2 |

### 4.3 推荐决策

**对于 Devrix，推荐采用 D-S-A-F-T 五层分层。**

理由:
1. **多智能体场景**: 需要清晰的业务分层来管理复杂度
2. **需求可追溯**: PRD Issue → 功能 → 测试用例完整链路
3. **长期维护**: 语义清晰的 ID 更易理解和协作
4. **扩展性**: 新增领域/场景成本可控
