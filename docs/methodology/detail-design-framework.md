# 详细架构设计框架



## ① 架构目标

- **业务目标**：解决什么业务痛点（如订单履约慢、跨系统数据孤岛）
- **技术目标**：量化指标——QPS/TPS、RT上限、可用性99.9%、数据一致性级别
- **约束条件**：合规（等保/GDPR）、预算上限、上线时间节点

---

## ② 架构原则

- **设计原则**：高内聚低耦合、面向失败设计（熔断/限流）、数据所有权原则
- **命名规范**：模块/服务命名统一前缀，REST路径采用 `资源/操作` 形式
- **代码风格**：工具类不过业务逻辑，异常不过模块边界，统一日志TraceId贯穿

---

## ③ 业务流程

- **核心用例时序图**：用户→前端→网关→服务A→服务B→DB，标注每步RT
- **异常补偿**：超时重试次数与间隔、失败后消息回溯、幂等保障
- **分支处理**：如支付失败→库存释放→消息通知，整条链路状态可追踪

---

## ④ 领域模型

- **聚合根**：业务完整性的最小边界（如订单聚合根含订单项、优惠、地址）
- **限界上下文**：按业务风险/变化频率划分（如"用户上下文"vs"订单上下文"）
- **领域事件**：订单已创建、库存已扣减、支付已超时——事件驱动跨上下文协同
- **模型图**：实体关系 + 聚合边界，颜色标注核心/支持/基础设施层

---

## ⑤ 核心链路图

- **端到端路径**：用户请求从网关到DB完整路径，标注每个节点的SLA承诺
- **时序标注**：每跳耗时占比，识别瓶颈（如DB查询占70%→需优化索引/缓存）
- **单点风险**：无冗余节点用红色标注，配套切换方案

---

## ⑥ 接口 / API 设计

- **风格**：RESTful为主，复杂查询用GraphQL，实时场景用WebSocket/gRPC
- **契约**：统一响应结构 `{code, message, data}`，错误码分层（系统/业务/参数）
- **幂等**：POST操作必带ClientToken或业务ID，防重复提交
- **版本**：URL路径版本 `/api/v1/` → `/api/v2/`，每个版本维护12个月
- **限流**：Header返回 `X-RateLimit-Remaining`，超限返回 `429 + Retry-After`
