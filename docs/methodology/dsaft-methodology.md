# DSAFT 架构方法论

> 定义软件的五层架构体系：**D 领域 → S 场景 → A 活动 → F 功能点 → T 测试点**。
> 核心思想：从抽象全貌到具体实现，每层有明确定义和归属关系。

---

## 一、精确定义

| 层级 | 定义 | 核心问题 |
|------|------|----------|
| **D 领域** | 业务能力边界，划分业务内聚区 | 系统由哪些业务领域组成 |
| **S 场景** | 用户达成完整目标的业务价值流 | 谁、为了什么、走哪条路径 |
| **A 活动** | 用户/调用方发起的具体业务动作 | 对外能做什么动作 |
| **F 功能点** | 可被 A 编排的最小业务/技术逻辑单元 | 内部由哪些功能点协作 |
| **T 测试点** | 不变的验证契约（WHAT，非 HOW） | 功能是否正确工作 |

---

## 二、设计理念

### 2.1 两大分段

```
┌─────────────────────────────────────────────────────────────┐
│  DS — 抽象层（概念稳定）                                    │
│    D  业务能力边界                                          │
│    S  达成目标的路径                                        │
├─────────────────────────────────────────────────────────────┤
│  AFT — 具体层（实现易变）                                   │
│    A  对外动作（入口契约）                                  │
│    F  对内功能点（编排实现）                                │
│    T  验收锚点（不变契约）                                  │
└─────────────────────────────────────────────────────────────┘
```

**稳定性梯度**：D/S 最稳定 → A/F 易变 → T 最稳定（不变契约）

### 2.2 自上而下（分解）

```
D 领域 → S 场景 → A 活动 → F 功能点 → T 测试点
   ↓         ↓         ↓         ↓
  包含      包含     编排      验证
```

### 2.3 自下而上（追溯）

```
T → F 或 A → S → D
↑    ↑         ↑    ↑
验证 归属      归属 归属
```

---

## 三、追溯规则

| 规则 | 说明 |
|------|------|
| S → D | 每个 S 必须归属一个 D |
| A → S | 每个 A 必须归属一个 S |
| F → A | 每个 F 必须归属一个 A |
| T → F 或 A | 每个 T 必须归属一个 F 或 A |

**说明**：T 可以归属 F（验证功能点，如单元测试），也可以归属 A（验证活动，如契约测试、E2E）。

---

## 四、ID 格式规范

嵌套归属编号，格式如下：

| 层级 | 格式 | 位数 | 示例 |
|------|------|------|------|
| D | D{1-9} | 1位 | D1 |
| S | D{X}-S{X} | 1+1位 | D1-S1 |
| A | D{X}-S{X}-A{01-99} | 1+1+2位 | D1-S1-A01 |
| F | D{X}-S{X}-A{XX}-F{01-99} | 1+1+2+2位 | D1-S1-A01-F01 |
| T | D{X}-S{X}-A{XX}-T{01-99} 或 D{X}-S{X}-A{XX}-F{XX}-T{01-99} | 1+1+2+2+2位 | D1-S1-A01-T01 或 D1-S1-A01-F01-T01 |

**T 归属规则**：
- T 归属 A：D1-S1-A01-T01（验证整个活动，如契约测试、E2E）
- T 归属 F：D1-S1-A01-F01-T01（验证具体功能点，如单元测试）

链路追溯示例：
D1-S1-A01-F01-T01
└─ D1: 交易领域
   └─ S1: 交易下单场景
      └─ A01: 下单渲染活动
         └─ F01: 获取商品详情功能点
            └─ T01: 商品信息展示正确测试点

## 五、层级定义

### 5.1 D 层：领域（Domain）

**定义**：业务能力边界，划分业务内聚区。

- 有自己的业务规则和 invariants
- 有自己的数据模型（不与其他领域共享）
- 通过 A 层（活动）与其他领域交互

**D 层注册表**：

| ID | 名称 | 类型 | 领域职责 |
|----|------|------|----------|
| D1 | {领域名} | 核心/支撑/公共 | {职责描述} |

**领域类型**：
- **核心域**：核心竞争力，直接创造用户价值
- **支撑域**：支撑核心域运转，不直接面向用户
- **公共域**：横向共享能力，为其他域提供通用服务。有自己的数据模型，通过 A 层暴露，保持内部内聚

### 5.2 S 层：场景（Scenario）

**定义**：用户达成完整目标的业务价值流。

**S 层注册表**：

| ID | 名称 | 触发条件 | 用户目标 | 涉及 A |
|----|------|----------|----------|---------|

**约束**：每个 S 必须归属一个 D

### 5.3 A 层：活动（Activity）

**定义**：用户/调用方发起的具体业务动作。

分为：
- **A-BE**：后端活动，原子业务步骤，有输入/输出/状态变更
- **A-FE**：前端页面，用户可见的路由级交互单元

**A 层注册表**：

| ID | 名称 | 类型 | 输入 | 输出 | 状态变更 |
|----|------|------|------|------|----------|

**约束**：每个 A 必须归属一个 S

### 5.4 F 层：功能点（Function）

**定义**：可被 A 编排的最小业务/技术逻辑单元。

分为：
- **F-BE**：后端功能点，可复用的逻辑计算或数据操作
- **F-FE**：前端模块，可复用的 UI + 逻辑单元

**F 层注册表**：

| ID | 名称 | 类型 | 输入 | 输出 |
|----|------|------|------|------|

**约束**：每个 F 必须归属一个 A

### 5.5 T 层：测试点（Test）

**定义**：不变的验证契约，描述 WHAT should work，而非 HOW。

**T 层注册表**：

| ID | 名称 | 归属层级 | 归属 ID | 验收契约 |
|----|------|----------|---------|----------|
| D1-S1-A01-T01 | {测试点} | A | D1-S1-A01 | {契约} |
| D1-S1-A01-F01-T01 | {测试点} | F | D1-S1-A01-F01 | {契约} |

**约束**：每个 T 必须归属一个 A 或 F

## 六、测试类型与层级映射

| 测试类型 | 验证范围 | 归属层级 | 执行时机 |
|----------|----------|----------|----------|
| 单元测试 | 单个 F 内部逻辑 | F | 每次构建 |
| 集成测试 | A 编排 + 多 F | A + F | CI |
| 契约测试 | 对外接口契约 | A | CI |
| E2E | 完整 S 用户体验 | A | 发布前 |

## 七、完整链路示例

### 核心域示例：D1（交易领域）

```
D1（交易领域 / 核心域）
└── D1-S1（交易下单场景）
    ├── D1-S1-A01（下单渲染活动）
    │   └── D1-S1-A01-F01（获取商品详情）
    │       └── D1-S1-A01-F01-T01（商品信息展示正确）
    │
    ├── D1-S1-A02（下单提交活动）
    │   ├── D1-S1-A02-T01（订单创建成功）← 归属 A，契约测试
    │   └── D1-S1-A02-F01（校验库存）
    │       └── D1-S1-A02-F01-T01（库存不足被拒绝）
    │
    ├── D1-S1-A03（库存预占活动）
    │   └── D1-S1-A03-F01（预占库存）
    │       └── D1-S1-A03-F01-T01（库存预占成功）
    │
    └── D1-S1-A04（支付回调活动）
```

### 公共域示例：D2（用户领域）

```
D2（用户领域 / 公共域）
├── D2-S1（身份认证场景）
│   ├── D2-S1-A01（登录活动）
│   │   └── D2-S1-A01-F01（校验凭证）
│   │       └── D2-S1-A01-F01-T01（无效凭证被拒绝）
│   └── D2-S1-A02（登出活动）
│
└── D2-S2（用户信息场景）
    ├── D2-S2-A01（获取用户信息活动）
    │   └── D2-S2-A01-F01（查询用户数据）
    │       └── D2-S2-A01-F01-T01（返回用户基本字段）
    └── D2-S2-A02（更新用户信息活动）
        └── D2-S2-A02-F01（写入用户数据）
            └── D2-S2-A02-F01-T01（更新成功后返回新版本）
```

> **说明**：公共域与核心域/支撑域结构完全相同（D→S→A→F→T），区别仅在于领域类型标记为“公共”。其 A 层天然可作为其他域的服务入口。

## 十二、Facet Decomposition 案例：ToolSurface + ToolFilter

DSAFT 不只描述"按 D 切领域"，也指导"按 Facet（面）切关注点"。
当一个领域有 N 个正交关注点（可见性 / 风险 / 调度 / 可观测性...）
同时被 N 个独立模块消费，**拆面**比**拆域**更适合。

### 12.1 反例：3 入口重复装配 + 6+ global singleton

```
NewContextEngine     → 注册 7 tool, 5 global var
buildWithGate        → 注册 7 tool, 5 global var (重复)
WireDelegate         → 注册 4 tool, 2 global var
```

- 每次"加 tool" → 改 3 处 + 1 global + 1 allowlist
- 每次"新 agent 模式" → 改 3 处 + 1 filter
- 6+ global singleton 让"谁注册了谁没注册"无法静态分析
- 任意一个 engine 漏注册一个 tool → LLM 收到 "unknown tool"

### 12.2 拆面契约定型（正交关注点）

```go
// shared/contracts/tool_surface.go
type ToolSurface interface {
    Name() string
    Tools(ctx, workDir, sessionID) []ToolSpec
    RiskLevel(name) RiskLevel
    Execute(ctx, name, input, workDir) (*ToolResult, error)
}

// shared/contracts/tool_filter.go
type ToolFilter interface {
    Apply(specs []ToolSpec, ctx FilterCtx) []ToolSpec
}
```

| 关注点 | 拆面契约 | 实现位置 |
|--------|----------|----------|
| "有什么 tool" | `ToolSurface.Tools()` | 每个 surface 一个文件 |
| "这个 tool 风险多大" | `ToolSurface.RiskLevel()` | 同上 |
| "执行 tool" | `ToolSurface.Execute()` | 同上 |
| "这个 agent 能看什么" | `ToolFilter.Apply()` | toolpolicy / per-risk / per-session |
| "执行链路" | `findSurface(name) → surf.Execute()` | turn_adapter |

### 12.3 拆面 vs 拆域

| 维度 | 拆域 (D-S-A) | 拆面 (Facet) |
|------|--------------|--------------|
| 切分依据 | 业务边界 (Bounded Context) | 关注点 (Concern) |
| 适用场景 | 多业务实体共变 | 同实体多关注点交织 |
| 复用方式 | 域内组合 | 跨域叠加 |
| 演化单元 | 整个域的 spec / design / impl | 单个面契约 + 一组实现 |
| 代价 | 跨域调用需 IPC / RPC | 跨面仅是 interface 组合 |

**判定**：当 ≥3 个模块**同时**需要"工具可见性 / 风险 / 调度"这三个关注点的
不同子集时，拆面比拆域收益高。

### 12.4 devrix 实战（DM-20260617-007）

| 指标 | 拆面前 | 拆面后 |
|------|--------|--------|
| 入口数 | 3 (NewContextEngine / buildWithGate / WireDelegate) | 1 (BuildSurfaces) |
| Global singleton | 12 个 | 3 (PR #63) → 0 (PR #64 目标) |
| "加 tool" 改动点 | 3 文件 + 1 global + 1 allowlist | 1 个 surface 文件 + 注册到 BuildSurfaces |
| 等价性测试 | 无 | `TestBuildWithGate_SupersetOfMainEngineTools` |
| 可发现性 | 注册 side effect | `devrix tool list` 直接 dump |

参考 OpenSpec change: `openspec/changes/devrix-tool-surface-contract/` (DM-20260617-007).

### 12.5 拆面 checklist

判断何时需要拆面：

- [ ] ≥3 个模块同时关心同一资源的多个正交维度
- [ ] 任意 1 个模块的变更会强制另外 N-1 个模块也改动
- [ ] "加一条规则" / "加一个 provider" 需要碰 ≥3 处
- [ ] process-wide global singleton ≥3 个
- [ ] 跨模块测试 setup 出现 `defer reset(global)` 反模式

满足 ≥3 条 → 启动 Facet Decomposition 拆面契约定型。
